## 2026-09-16

- **Time spent**: ~[fill in]
- **Rough tokens used**: ~[fill in]
- **What shipped**: First working slice of the MVP's Moodle connection and change-detection loop, in a new `Esmerelda/` app (backend + frontend), all under `backend/`:
  - `moodle/browser.py` — Playwright connector using a persistent Chromium profile (`browser_profile/`) so login only has to happen once per machine; prompts for manual login when the session isn't already authenticated, then reads active courses by locating Moodle's "Only courses in progress" dashboard text and matching it against `/course/view.php` links.
  - `course_radar.py` — reworked active-course detection to be less dependent on that dashboard text: matches course names against a regex for the current term's course codes (`BUAN`/`DESG`/`VATS` + `2026/27S1`) instead, and moved the persistent browser profile under `moodle/browser_profile/` so all scripts share one logged-in session.
  - `content_radar.py` — for each active course, walks its sections and activity links, classifies each item by type (PDF, PowerPoint, Assignment, Quiz, Video, Forum, etc.) from the link/href, and filters out navigation/UI noise. Persists results to `state/content_snapshot.json` and diffs the new scrape against the last one to find newly-added items — this is the change-detection piece from the plan, so the same resource doesn't get reported twice.
  - `submission_radar.py` — scans Moodle's Timeline block for entries matching "is due", walks up the DOM from each link to find the owning course, deduplicates by assignment+course, and turns the result into a short spoken briefing via `pyttsx3` (e.g. "You have 2 upcoming submissions..."). This is the first text-to-speech output for the proactive digest — earlier than planned (final goals listed real voice I/O as post-MVP), but it was a natural fallback once `voice.py`'s simple `EsmereldaVoice` wrapper class was working.
  - `voice.py` — small standalone `EsmereldaVoice` class wrapping `pyttsx3` (rate/volume set, `speak()` method), used as the first voice-output test before folding TTS into `submission_radar.py`.
  - `frontend/` — scaffolded a Vite + React + TypeScript app; still the default template, not yet wired to the backend.
  - Known rough edges going into the next session: `course_radar.py`'s active-course regex is hardcoded to this term's course codes and will need updating (or a more general rule) next term; `content_radar.py`'s course list is hardcoded rather than pulled from `course_radar.py`'s output; the two active-course-detection approaches (`browser.py`'s text-based one and `course_radar.py`'s regex-based one) haven't been consolidated into one.

    - *act* — each step calls real `queries.py` functions and, for anything assignment-related, `assignment_action_planner.plan_actions`.
    - *observe* — each step appends real findings to a shared context (deduped by id).
    - *iterate* — the loop runs every reasoned step before composing the final reply, so a compound message (a course name plus "documents") triggers more than one real query in a single turn.
    - Explicitly rule-based throughout — no LLM call — and says so in its own docstring and in the reply the frontend shows under "Esmerelda" (`rule-based agent over your real course data, not a generative model`), per this task's "do not fabricate" instruction.

## 2026-09-18 (Fix: repeated Moodle syncs failed after the first — login success was judged by URL, not by real page state)

- **The reported bug**: the very first sync with a given set of credentials succeeded; every sync after that failed with `"Moodle did not accept the configured credentials (still on the login page after submitting)."`, with the credentials genuinely unchanged.
- **Investigated each of the six specific questions asked, in order**:
  1. **How is the browser/context created for every sync?** `run_sync()` opens a brand-new `sync_playwright()` context and calls `p.chromium.launch(headless=True)` **fresh on every call** — never reused across calls, never `launch_persistent_context()`. Confirmed by reading the code, not assumed.
  2. **Are cookies/localStorage/session state/browser profiles reused?** Before this fix, `run_sync()` called `browser.new_page()`, which uses Playwright's *implicit default context* on that `Browser` object rather than an explicitly-created one. Since `browser` itself is a brand-new process every call, this still could not leak state *between* `run_sync()` calls — but it also meant isolation was never made explicit or provable. **This is now made explicit and directly tested**: `run_sync()` calls `browser.new_context()` before `context.new_page()`, and the new regression test (`tests/test_sync_service.py`, checks 5/5b/5c) runs two fully independent `_login()` sessions against a real local server and asserts the server saw **two real login POST requests**, not one login followed by a reused-cookie freebie — proving, not just arguing, that no session state crosses between syncs. **Conclusion: this was not the actual bug**, but the code is now more explicit and provably isolated regardless.
  3. **Is the login page cached or stale?** `page.goto(moodle_url, wait_until="domcontentloaded")` is a real navigation on a brand-new page/context every time; Playwright's default context has no HTTP cache pre-seeded, and nothing in this codebase configures Playwright's cache behavior at all. No evidence this was a factor.
  4. **Does Moodle redirect to a different URL after login?** **Yes — this turned out to be the actual root cause.** The pre-fix success check was `page.wait_for_url(re.compile(r"^(?!.*login).*"), timeout=20000)` — "wait until the URL stops containing the substring 'login'." Real Moodle installs commonly carry a `wantsurl`/`returnurl`/session query parameter through the post-login redirect chain, and that carried-through URL can itself still contain the substring "login" (e.g. if the page the user was trying to reach before being bounced to the login form was itself login-adjacent, or if Moodle's session-key-refresh step temporarily revisits a URL under `/login/`) even though the login **genuinely succeeded**. A URL-substring check cannot tell "still failed to log in" apart from "logged in, but momentarily on a URL that happens to contain the word login" — it was guessing, not verifying.
  5. **Does Moodle present a different page/form on subsequent logins?** Plausible in general (a "remember this device" prompt, a forced password-change notice, a consent screen shown once) but not confirmed either way — no live Moodle access in this environment. The fix (see below) is robust to this regardless, because it no longer depends on knowing Moodle's exact page/redirect shape in advance.
  6. **Does the code determine success ONLY by URL?** **Yes, exactly as suspected — this was the bug.** `_login()` had exactly one success signal (the URL regex above) and exactly one failure signal (that regex timing out). No DOM element was ever inspected to check whether the login form was actually gone, whether a logged-in-only element was actually present, or whether Moodle had displayed an explicit login-error message.
- **The fix — replaced the URL-only check with real DOM-based verification**:
  - Login success is now judged by `_is_logged_in(page)` — the presence of a real logged-in-only DOM element (`a[href*='/login/logout.php'], .usermenu`, standard across Moodle's default theme) — **and** the absence of the login form (`_has_login_form(page)`), never the URL. The URL is now used only for diagnostic logging, never as evidence.
  - If neither a logged-in marker nor the login form is found after waiting, or if Moodle's own login-error element (`#loginerrormessage, .loginerrors, .alert-danger`) is present, `_login()` raises `MoodleLoginError` with the **real, DOM-derived error text Moodle displayed** (when there is one) instead of a generic guess — genuinely more actionable for diagnosing a real future failure, and still never includes the password.
  - Replaced the single `wait_for_url()` race with `page.wait_for_load_state("networkidle", timeout=15000)` (best-effort — a timeout here is not itself treated as failure, the DOM checks after it are the real verdict) so Moodle's redirect chain has time to settle before those DOM checks run.
  - `run_sync()` now explicitly opens `browser.new_context()` (previously relied on `browser.new_page()`'s implicit default context) and always closes both `context` and `browser` in a single `finally` block, even if `context` creation itself partially failed (guarded by `if context is not None`).
- **Diagnostic logging added** (`_log_diagnostics()`, called at three points: `before_login`, `immediately_after_submit`, `after_waiting_for_redirect`) — logs, via the standard `logging` module under logger name `esmerelda.moodle_sync`: the current URL, the page title, whether the login form is present, whether the logged-in marker is present, and the text of any Moodle-displayed login/error message. **Never logs**: the username, the password, cookies, tokens, or any other session data — confirmed by grepping the file for every use of `password`/`username`, which are only ever passed to `_get_credentials()`'s return tuple and `page.fill()`, never to `logger.info()` or any string formatting.
- **New regression test** (`tests/test_sync_service.py`, section 5): a real, minimal local HTTP server (stdlib `http.server.ThreadingHTTPServer`, no external test dependencies added) that behaves like a Moodle login flow — a login form on `GET`, a session cookie + redirect on a correct `POST`, a logged-in-only marker element once authenticated, and a real login page again on an incorrect `POST`. The real `_login()` function is run against it, twice, as **two fully independent Playwright browser launches** (mirroring `run_sync()`'s exact browser/context lifecycle) — exactly the reported scenario: sync → successful login → context/browser closed → sync again → successful login. Also verifies a genuinely wrong password still raises `MoodleLoginError` rather than a false success. **5/5 new checks passed** (12 pre-existing + these = **16/16** in this file).
- **Verification**:
  - `tests/test_sync_service.py`: **16/16 passed**, including the new regression test — a real headless Chromium was launched twice against a real local server in this run, not mocked.
  - Re-ran the other three suites: `test_groq_agent.py` (10/10), `test_assignment_action_planner.py` (9/9), `test_followups.py` (9/9) — **44/44 total, no regressions.**
  - `main.app` still imports cleanly.
  - `git status` confirms only `backend/moodle/sync_service.py` and `backend/tests/test_sync_service.py` changed this step — the database, frontend, and sync-scheduling/trigger logic (`api/routes.py`, `storage/models.py`, `storage/crud.py`) were not touched, per the instruction to leave them alone unless required for the authentication fix itself (they were not required).
