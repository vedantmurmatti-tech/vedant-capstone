## 2026-09-16

- **Time spent**: ~[fill in]
- **Rough tokens used**: ~[fill in]
- **What shipped**: First working slice of the MVP's Moodle connection and change-detection loop, in a new `Esmerelda/` app (backend + frontend), all under `backend/`:
  - `moodle/browser.py` — Playwright connector using a persistent Chromium profile (`browser_profile/`) so login only has to happen once per machine; prompts for manual login when the session isn't already authenticated, then reads active courses by locating Moodle's "Only courses in progress" dashboard text and matching it against `/course/view.php` links.
  - `course_radar.py` — reworked active-course detection to be less dependent on that dashboard text: matches course names against a regex for the current term's course codes (`BUAN`/`DESG`/`VATS` + `2026/27S1`) instead, and moved the persistent browser profile under `moodle/browser_profile/` so all scripts share one logged-in session.
  - `content_radar.py` — for each active course, walks its sections and activity links, classifies each item by type (PDF, PowerPoint, Assignment, Quiz, Video, Forum, etc.) from the link/href, and filters out navigation/UI noise. Persists results to `state/content_snapshot.json` and diffs the new scrape against the last one to find newly-added items — this is the change-detection piece from the plan, so the same resource doesn't get reported twice.
  - `submission_radar.py` — scans Moodle's Timeline block for entries matching "is due", walks up the DOM from each link to find the owning course, deduplicates by assignment+course, and turns the result into a short spoken briefing via `pyttsx3` (e.g. "You have 2 upcoming submissions..."). This is the first text-to-speech output for the proactive digest — earlier than planned (final goals listed real voice I/O as post-MVP), but it was a natural fallback once `voice.py`'s simple `EsmereldaVoice` wrapper class was working.
  - `voice.py` — small standalone `EsmereldaVoice` class wrapping `pyttsx3` (rate/volume set, `speak()` method), used as the first voice-output test before folding TTS into `submission_radar.py`.
  - `frontend/` — scaffolded a Vite + React + TypeScript app; still the default template, not yet wired to the backend.
  - Known rough edges going into the next session: `course_radar.py`'s active-course regex is hardcoded to this term's course codes and will need updating (or a more general rule) next term; `content_radar.py`'s course list is hardcoded rather than pulled from `course_radar.py`'s output; the two active-course-detection approaches (`browser.py`'s text-based one and `course_radar.py`'s regex-based one) haven't been consolidated into one.

## 2026-09-17 (implemented POST /api/chat — a real, rule-based agent)
- **Time spent**: ~[fill in]
- **Rough tokens used**: ~[fill in]
- **What shipped**: Implemented the `/api/chat` endpoint that was previously missing (the prior session's chat page always threw `ChatUnavailableError`). Checked first — no Claude Code Skill named `assignment-action-planner` exists anywhere in this repo's `.claude/skills/`, the plugin catalog available to this session, or the filesystem more broadly (confirmed with a full-disk `find`) — so "integrate the custom assignment-action-planner Skill" was implemented as a named backend planning module fulfilling that role, documented as such at the top of the file so it's easy to correct if a different skill was actually meant.
  - **Backend refactor — `backend/api/queries.py`** (new): pulled every DB query and every ORM-row-to-response-model conversion out of `routes.py` into one shared module, so the new chat agent and the existing REST routes call the exact same functions instead of duplicating query logic. `routes.py` is now a thin HTTP layer over `queries.py`; behavior is unchanged (re-verified every existing endpoint still returns 200 after the refactor).
  - **`backend/api/assignment_action_planner.py`** (new) — the requested planning component. Pure rule-based reasoning over real `Assignment` rows: classifies each into overdue/due-soon/upcoming/unscheduled using the same 48-hour threshold as `getAssignmentUrgency` in the frontend (so the plan it produces agrees with what the UI already shows), sorts by urgency then due date, and renders a short numbered action plan with a plain-language recommendation per item. No model call anywhere in it.
  - **`backend/api/chat_agent.py`** (new) — the agent loop itself, explicitly structured as perceive → reason → act → observe → iterate:
    - *perceive* — keyword-matches the message against four intents (deadlines / documents / sync / help) and separately checks whether it names a real course (by course code or by the subject text after the last `-` in `Course.name`, e.g. "Tangible Interfaces").
    - *reason* — turns that into a bounded list of steps (`MAX_STEPS = 3`) — a matched course always short-circuits to a single `course_lookup` step (which itself gathers assignments + resources + optionally documents for that course), otherwise each matched intent becomes its own step.
    - *act* — each step calls real `queries.py` functions and, for anything assignment-related, `assignment_action_planner.plan_actions`.
    - *observe* — each step appends real findings to a shared context (deduped by id).
    - *iterate* — the loop runs every reasoned step before composing the final reply, so a compound message (a course name plus "documents") triggers more than one real query in a single turn.
    - Explicitly rule-based throughout — no LLM call — and says so in its own docstring and in the reply the frontend shows under "Esmerelda" (`rule-based agent over your real course data, not a generative model`), per this task's "do not fabricate" instruction.
  - **`backend/api/schemas.py`** — added `ChatRequestIn` (validated `message: str`, 1–2000 chars — an empty body now correctly 422s), `ChatSourceOut`, `ChatResponseOut` (`reply` plus real `assignments`/`courses`/`documents`/`sources`/`followUps` arrays, all built from the same `AssignmentOut`/`CourseOut`/`DocumentOut` models the REST endpoints already return).
  - **`backend/venv/main.py`** — bug found and fixed during integration testing: `CORSMiddleware` only allowed `GET`, so every `POST /api/chat` call failed the CORS preflight from the browser (`net::ERR_FAILED`, confirmed in a Playwright console-error capture before the fix). Added `POST` to `allow_methods`.
  - **Frontend — `frontend/src/lib/api.ts`**: `sendChatMessage` now POSTs to the real endpoint and returns the typed `ChatApiResponse` instead of always throwing; `ChatUnavailableError` is now reserved for genuine connectivity/HTTP failures (network down, non-2xx), not "no endpoint exists". `frontend/src/types/index.ts` gained `ChatApiResponse` and extended `ChatMessage` with optional `assignments`/`courses`/`documents` so the chat UI can render real referenced records, not just prose.
  - **`frontend/src/pages/Chat.tsx`** rewritten to call the real agent: a genuine "Thinking…" state while the request is in flight (real latency, not theater), assistant replies render through the existing `ChatMarkdown` component plus new inline chips for any assignments (urgency dot + real due date, linking to the course), courses (linking to `/courses/:id`), and documents (linking to the real download endpoint) the agent returned. The header subheading now reflects actual reachability (`Online` / `Unreachable`, driven by whether the last request succeeded) instead of a hardcoded label — caught and fixed after noticing it still said "Online" in a screenshot taken with the backend deliberately killed.
  - **Bug found & fixed mid-session**: the first "priority plan" follow-up chip read "Tell me more about the top one" — since the agent is stateless (no conversation memory), that phrase doesn't match any intent or course and fell through to the fallback reply on click (reproduced and screenshotted). Changed it to name the actual top-priority assignment's course by code (e.g. "Tell me more about DESG319"), which does resolve via the course-matching logic on the next turn — verified by clicking it and confirming a real course lookup came back.
  - **Verification** (all run against the live app, not simulated): `npx tsc -b` and `npm run build` clean. Backend restarted and every endpoint curl-tested individually: `help`, `deadlines` ("what is due this week"), course lookup ("tell me about tangible interfaces"), compound course+documents ("what documents do you have for tangible interfaces" — correctly reported 0 real documents for that specific course), sync status, fallback (nonsense input), and empty-message validation (422). Confirmed the refactor didn't regress `/api/courses`, `/api/assignments`, `/api/documents`, `/api/sync-status`, `/api/dashboard/summary` (all still 200). Drove the running frontend with Playwright: sent real messages through the chat UI end to end (zero console errors after the CORS fix), clicked a follow-up chip and confirmed a second real agent turn, killed the backend process and confirmed the chat page showed the honest "unreachable" state with the real error message (not a canned one) and the header switched to "Backend offline", restarted the backend and confirmed it recovered. Final full-route regression pass (`/dashboard`, `/courses`, `/courses/1`, `/assignments`, `/documents`, `/chat`, `/settings`) — zero console errors, zero failed `/api/*` requests.
  - **Known limitations**: the agent has no conversation memory across turns (each message is perceived independently — a follow-up like "what about that one" won't resolve unless it names something concrete); intent matching is keyword-based, not semantic, so it will miss paraphrases a real language model would catch; `assignments_count` in the demo dataset is only 2, so the "deadlines" and "priority plan" paths were exercised with real but small data — course lookups against the 6 other courses (which have 0 tracked assignments each) were used to confirm the empty-case reply text.
- **Recommended next step**: if genuine natural-language understanding is wanted later, the perceive step is the natural place to swap keyword-matching for an actual LLM call — the reason/act/observe structure and the `assignment_action_planner` module would not need to change.
